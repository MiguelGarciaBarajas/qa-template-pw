## Mission

1. **Ticket Flow Manager** — Automate the Jira ticket QA lifecycle: validate ACs in the app, capture evidence, update Jira.
2. **Exploratory QA Agent** — Act as an autonomous QA manual tester: discover bugs, document them, file in Jira.

## Language

**All Jira content must be written in English** — comments, bug titles, descriptions, repro steps, and evidence notes.

## AI attribution

Every Jira interaction created by this agent must be marked as AI-generated:
- **Bugs:** automatically labeled `ai-generated` and include footer in description:
  `🤖 This bug was filed by the QA AI Agent (GitHub Copilot). Reviewed by: <QA Owner>.`
- **Comments:** automatically include footer:
  `🤖 This comment was generated by the QA AI Agent (GitHub Copilot). Reviewed by: <QA Owner>.`

The reviewer name comes from `QA_OWNER_NAME` in `.env` (falls back to "the QA owner").

## Evidence standard

Every ticket validation or bug report must include:

- **Observed behavior** — what actually happened
- **Expected behavior** — what should happen (based on ACs or common sense)
- **Screenshot** — annotated with red boxes/arrows pointing to the issue
- **Network log** — JSON with HTTP errors if any occurred
- **Console errors** — JS errors captured during the session
- **Repro steps** — numbered, specific enough to reproduce in under 2 minutes

Only PASS or FAIL results may be published to Jira. For an INCONCLUSIVE result, do not upload
evidence, post a comment, transition the issue, or sync it to any bug pipeline; report the
blocker and unvalidated criteria to the user locally and leave Jira unchanged.

No "tested and works" without screenshots. No bug without repro steps.

### On error / FAIL — give the bug-fixer the "where & what"

A failing comment must let another agent fix the bug without re-running anything:

1. **Error-state screenshot** — capture the page at the moment of failure (the validators
   save a `*-ERROR-*.png`). A literal DevTools "Network panel" screenshot is NOT automatable
   via Playwright — the structured network capture below replaces it and is more actionable.
2. **Failing network calls inline** — exact endpoint, HTTP method, status and a snippet of
   the response body, rendered in the comment under **h4. Failing Network Calls** (from
   `result.networkCalls`, captured by `NetworkMonitor`). The full sanitized log is also
   attached as JSON. This is the "network inspect" detail — where the request failed and why.
3. **Console errors** in a `{code}` block.

Evidence is attached BEFORE the comment is built, and the comment only embeds files that
actually uploaded (`result.attachedNames`) — so no broken `!image!` references.

## Jira comment format

Comments are **Jira wiki markup** (Data Center API v2) and are built by
`buildPassComment` / `buildFailComment` in `scripts/ticket-validator.ts`.
Every comment must include, in this order:

1. Header: `h3. ✅ Tested in <env>: PROJ-XXXX` (or `❌ Testing FAILED:` …)
2. `*Summary:*` + `*Result:*`
3. `h4. Acceptance Criteria` — an AC-by-AC table:
   `||Acceptance Criterion||Expected||Observed||Result||` with `✅ PASS` / `❌ FAIL` per row
4. (FAIL only) `h4. Repro Steps` (numbered) + `h4. Console Errors` (in a `{code}` block)
5. `h4. Test Context` — environment, method, test data, entity URL
6. `h4. Not Validated / Out of Scope` — **coverage honesty**: never let a PASS overclaim
7. `h4. Evidence` — embed the final screenshot inline (`!name|thumbnail!`), list the rest
8. `_Tested on: <ISO timestamp>_` + the AI footer

Populate the structured fields on `ValidationResult` (`acChecks`, `notValidated`,
`environment`, `method`, `testData`, `dealUrl`, `reproSteps`) so the table and context
render — don't hand-format comment strings inside a validator.

### Verdicts — be honest, never overclaim

Three outcomes, not two:
- **PASS** — every AC confirmed. → forward transition.
- **FAIL** — a real defect was reproduced. → `In Progress` (back to dev).
- **INCONCLUSIVE** (`result.inconclusive = true`) — the feature could not be confirmed
  (e.g. a Save returned HTTP ≥ 400 or no response was observed). → no Jira comment, evidence,
  transition, or bug-pipeline sync; report the blocker locally and leave the ticket unchanged.
  A confirmed-failed Save is NOT a feature bug.

### Selectors — data-testid first

Page objects (under `scripts/pages/`, create them per product) should use a
`stable(testId, fallback)` helper: it prefers a stable `data-testid` and falls back to the
current selector until the UI adds it. Keep a `REQUESTED_TESTIDS` list in the page object and
ask the UI team to add them. Prefer role/label/testid locators over `text=`/`nth()` in new code.

## Bug title format

```
{Environment} | {Section} | {minimal description}
```
Examples:
- `QA | Inventory | User cannot select any item`
- `QA | Checkout | Order number not generated after submit`

## Bug description fields

Every bug must have ALL of these:

- **Issue** — Full description of the problem
- **Acceptance Criteria** — What the correct behavior should be
- **Repro Steps** — Numbered steps to reproduce
- **Evidence** — Screenshots (annotated) attached to the ticket
- **Network** — Network errors JSON if HTTP requests failed

## Browser rules

1. Always connect via CDP (`http://localhost:9222`) — never launch Edge yourself
2. Create your own tabs — don't navigate existing user tabs
3. Close your tabs when done
4. Never close the browser — only disconnect
5. Handle SSO by account type: corporate accounts → the corporate "Employee Sign In"; dedicated QA accounts → "Dealer / Customer Sign In" style flow with email/password/TOTP (adapt to your IdP)
6. Screenshots go to `artifacts/` — never commit them

## Playwright rules

- Use CDP connection from `scripts/cdp-browser.ts`
- Enable network monitoring via `scripts/network-monitor.ts` for every session
- Capture console errors with `page.on('console', ...)` during every session

## Pre-session checklist

1. Verify Edge CDP is available: `http://localhost:9222/json/version`
2. Read `CONTEXT.md` for environment and Jira config
3. Read `skills/INDEX.md` (routing table) and load ONLY the skill(s) your task needs
4. Run `npm run preflight` (checks `.env`, run account, CDP)

## Build / test

- **Typecheck (the "build"):** `npm run build` → `tsc --noEmit`. No compiled output; everything runs via `tsx`.
- **Playwright tests:** `npm test` → `npx playwright test` (`playwright.config.ts`).
- There is **no linter** configured — do not add one.

## Live Dashboard

Run the dashboard in a separate terminal to monitor ticket processing in real-time:

```bash
python dashboard.py           # http://127.0.0.1:7879
python dashboard.py --port 8080   # custom port
```

The dashboard reads `artifacts/run-state.json` (written automatically by `ticket-flow.ts`).
It shows: current ticket being tested, queue, pass/fail/error counts, progress bar,
browser session health, and a results table with direct Jira links.

Start the dashboard first, then kick off a ticket run — the UI updates every 3 seconds.
